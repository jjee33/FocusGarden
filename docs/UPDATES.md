# Updates

How a running copy of Focus Garden learns that a newer one exists, and what it is
allowed to do about it.

Owned by `autoload/update_manager.gd`. The release side is
[RELEASE.md](RELEASE.md).

## What the app does, exactly

Once, about six seconds after launch, an exported build makes a single HTTPS GET
to:

```
https://github.com/jjee33/FocusGarden/releases/latest/download/latest.json
```

It sends no cookies, no identifiers and no telemetry — just the request, with a
`User-Agent` of `FocusGarden/<version>`. GitHub sees an IP address and a version
string, the same as any download would show it. Nothing is sent about the
player, their garden, or their sessions, because nothing about them is ever read.

That request is the **only** network call in the codebase. There is no second
one, no analytics, no crash reporting, no license check. If `check_for_updates`
is off in Settings, there is no first one either.

Nothing happens in the editor. `UpdateManager.is_available()` is
`OS.has_feature("template")`, so development runs and every headless gate stay
offline — which is also why the test suite has no dependency on GitHub being up.

## Why a manifest and not the GitHub API

`releases/latest/download/<name>` is a stable URL that always redirects to the
newest release's asset of that name. Compared with `api.github.com`:

- no token, and no unauthenticated rate limit worth hitting
- no JSON schema that can change under us
- somewhere to put a **SHA-256 per asset**

The last one is the reason. The app is about to hand a downloaded file to the
operating system and let it run. Verifying it against a digest published over TLS
from our own release page is the difference between an update and an arbitrary
executable.

## The manifest

Generated by `tools/make_manifest.py` in the `publish` job, from the files that
are actually being uploaded. It is never written by hand — a checksum that
describes a different build is worse than no checksum.

```json
{
  "version": "0.2.0",
  "released": "2026-08-25",
  "notes_url": "https://github.com/jjee33/FocusGarden/releases/tag/v0.2.0",
  "notes": "First release with installers…",
  "platforms": {
    "windows": {
      "url": ".../FocusGarden-Setup-0.2.0.exe",
      "sha256": "…",
      "size": 108003328
    },
    "linux": {
      "url": ".../FocusGarden-0.2.0-x86_64.AppImage",
      "sha256": "…",
      "size": 112000000
    }
  }
}
```

`notes` is the first paragraph of the CHANGELOG section, capped — enough for a
dialog. The full text is behind `notes_url`.

## The flow

1. **Check.** Fetch the manifest. Compare `version` with
   `application/config/version` using `VersionUtil.is_newer`, which compares
   numerically and treats anything unparseable as `0.0.0` so a malformed manifest
   can never look newer.
2. **Announce.** A toast, plus a permanent row in Settings → Updates. **Not while
   a focus session is running** — the notice waits for `session_completed`. A
   session is the one thing the app exists to protect, and no update is worth
   interrupting one (§3).
3. **Download**, only when the player asks. Into `user://updates/`, with progress.
4. **Verify.** SHA-256 against the manifest. On a mismatch the file is deleted and
   the player is told. Nothing is executed.
5. **Install**, after a confirmation that says the app will close.

## Installing

**Windows.** Runs the downloaded Inno Setup installer with
`/SILENT /NORESTART /CLOSEAPPLICATIONS /relaunch=1`, then quits. The install is
per-user (`%LOCALAPPDATA%\Programs\Focus Garden`), so there is no UAC prompt —
which is precisely what makes a one-click update possible. `relaunch=1` is read by
the `ShouldRelaunch` check in `packaging/windows/FocusGarden.iss`; without it the
app would close to update and never come back, because Inno skips `postinstall`
entries under `/SILENT`.

**Linux.** Only when `$APPIMAGE` is set — that is, when the running build really is
an AppImage. The new file is staged as `<path>.new`, made executable, and
`rename`d over the original. Rename is atomic, and the running process keeps the
old inode mounted, so a build can replace itself while executing. An extracted
AppDir or a distribution package has an empty `$APPIMAGE` and is never touched;
those offer the release page instead.

**Anything else** — a platform with no asset in this release, a build we do not
own — gets a button that opens the release page. Offering an install that cannot
be performed would be worse than saying so.

## Withdrawing a bad release

**Never re-tag.** A tag that already exists is refused by `tools/release.ps1`, and
moving one would leave some players with a build that claims a version it is not.

- **Delete the GitHub Release.** `latest` falls back to the previous one, and
  copies that have not updated yet stop being offered it. Keep or delete the git
  tag as you like; it has no effect on `latest`.
- **Or publish a higher version**, which is usually better: anyone already on the
  bad build gets pulled forward rather than left there.

Note the asymmetry — deleting a release does not roll anybody back. Someone who
already installed it stays on it until something newer exists. That is the case
for fixing forward.

## Turning it off

Settings → Updates → *Check for updates*. Off means no request is ever made,
including at launch. The preference is `check_for_updates` in the save file,
defaults to on, and is covered by
`tests/unit/test_models.gd::test_update_checking_defaults_on_but_stays_off_once_refused`
— because a default that quietly reasserted itself would make the toggle a lie.

## Testing a change to any of this

The update path cannot be exercised from the editor by design, so:

1. Build and install two versions, an older and a newer.
2. Run `workflow_dispatch` on the release workflow to produce real artifacts
   without publishing, or publish a real pre-release from a branch.
3. Launch the older build and watch Settings → Updates through the whole flow.
4. Corrupt a `sha256` in the manifest and confirm the install is refused with a
   clear message and no partial write.
5. Disconnect the network and confirm launch is silent and unblocked.

`VersionUtil` itself is unit tested — `tests/unit/test_version_util.gd` — and that
is where the comparison edge cases belong, not in a manual pass.
